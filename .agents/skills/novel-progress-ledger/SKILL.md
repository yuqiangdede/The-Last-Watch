# novel-progress-ledger｜全书创作进度台账

## 目标和强制入口

用户要求“查看进度、更新进度表、写完了哪一卷哪一章、哪章审过、最新评分”“维护创作进度”时执行此 Skill。任何四阶段创作/授权修订、完成有报告的质量审核、章纲换版/拆章、正文版本变动以后也必须调用本 Skill 的同步步骤。此 Skill 只追踪进度，不替代 chinese-novelist 的四阶段质量协议，不代写正文，不自动进行未授权审核。

**相邻上游一致性门禁**：审核结论在登记台账前必须执行 [stage-consistency-gate.md](../chinese-novelist/references/guides/stage-consistency-gate.md)：卷纲对全书大纲、章纲对卷纲、简写对章纲、正文对简写；确证实质偏离登记结果 **`不通过`**（报告中写明“打回”），资料不足或版本待决登记 **`待核实`**（不得冒充不一致或通过）。**审核已完成但被打回**仍算已审事件，绝不当作审核通过或允许进入下一环节。原有脚本 STATUS 可直接表示“通过/不通过/待复核/待核实”，不新增评分字段。

**项目主视图**：`05-写作计划/创作阶段进度.md`（GitHub直接可读，20卷总览＋每章明细）；**机器镜像**：`05-写作计划/创作阶段进度.csv`。二者都是只读生成物，**不允许人工直接改行、补分**。**卷纲有效审核指纹**：当某卷存在唯一现行独立卷纲时，对该卷审核须绑定该独立卷纲的SHA256，而非全书卷导航；没有或有多个不确定候选时，保守回退总卷纲并标示版本限制。这样其他卷修改总导航不应使本卷真实审核误判为失效。**审核事件唯一源**：`05-写作计划/阶段审核记录.json`（结构化留存历次经过证据核查的阶段审核）；正文已存在的官方终审注册表仍以 `08-审稿/章节最终审核总表.csv`／XLSX 及正式报告为准，不重复建立正文评分权威。

## 写作准入与审核状态区别（强制）

每次新写成果物，调用 [stage-entry-gate.md](../chinese-novelist/references/guides/stage-entry-gate.md)：**写章纲要求现行卷纲正式审核通过；写简写要求对应现行章纲正式审核通过；写正文要求对应现行简写正式审核通过**。从审核事件与实际报告核对目标范围、版本指纹和结果必须为 `通过`，不得仅凭“已写”“已审（作者确认）”或高分、旧版报告放行。记录不存在、已过期、结果不通过/待复核/待核实均阻断下游新稿；此表只显示状态，不能单独替代审核证据。阶段审核记录格式沿用旧 schema，不虚构新记录，也不擅自篡改作者历史确认。对既有成品执行审核或安全修订不因历史记录缺失而被禁止。

## 四阶段口径（每章必须分别填两个状态）

| 阶段 | “已写”的可核依据 | “已审核”的可核依据 |
| --- | --- | --- |
| 卷纲 | 卷大纲中确有该卷条目，或本卷现行卷级细纲已存在 | 对应卷纲的当次真实审核报告、结论、受审版本；只审其他卷不算 |
| 章纲 | 现行可执行章大纲中确有该篇目；停用旧稿无效 | 该章或明确覆盖全卷每一章的真实章纲审核报告 |
| 章简写 | 对应编号章／独立插章的实际简写源文件存在 | 逐篇七维剧情审核，有结论和实际报告（不能以“简写已确认”自动代替） |
| 章正文 | 对应编号章／独立插章的实际正文 MD 存在 | 正文审核报告与有效审稿记录已核；AI味37项另列，不可制造“AI味分数” |

- **写完≠审完，已审核≠审核通过，作者定稿≠AI审稿通过；正文文学审查≠TXT/合订本工程验收**。相邻上游不一致一票打回，即使历史审核分数达标也不得冒写“通过”；上游未核实应显示“待核实”。单章显示“已写/未审”“已写/已审:通过(分数)”或“需复审(源稿已改)”。确认无法取得报告时明确“无正式审核记录”，不得从作者人工精读、写作阶段、文件名或旧分数推断。
- 事件审核登记须检查实际报告存在，并绑定受审稿的 SHA256；源稿修改后保留历史记录，但最新状态提示**需复审**。只有报告真正覆盖对应篇目才逐篇登记，禁止用一次抽样、某卷审阅概述批量填全部章节。
- 正文终审总表 CSV 在本 Skill 中**只读引用**，不取代其 XLSX 更新协议。CSV 中只有基线 commit、未记录最终文件哈希的，标记“原记录，版本待核”，分数仍如实展示，不误称当前版本已复审或工程已验收。
- **独立插章独立一行**，不占普通章流水号；第NN卷卷内编号与全书章号不得互换，旧章纲禁用不能参与当前进度统计。未拆章卷按卷级行显示“章数未定”，不杜撰章节号。所有未确定的情节仍只是规划。
- 本表维护的是机器创作／质量进度，**禁止修改** `07-创作记忆/作者人工复核进度.md`，除非作者在本次对话明确要求专门更新该文件；也不自动修改正文、简写、章纲、`05-写作计划/章节规划总表.md`、历史审稿报告或已经存在的最终审核 XLSX。
- 任何审稿结论和分数继续依 `chinese-novelist` 对应四阶段正式量表，正文AI味37项不数值化。卷纲/章纲与简写、正文分数不同量表，绝不能混算成跨阶段均分。


## 作者明确确认的历史阶段状态（与正式审核报告分开存证）

当作者明确指出“某些卷的四阶段已经写完／审核完成”，应记录在项目 `05-写作计划/创作阶段状态确认.json`，按卷、按阶段保存 `written` 与 `reviewed` 两个布尔字段，并注明确认日期、依据和适用范围。此记录用于纠正项目历史迁移时漏记的**流程状态**，即使部分旧简写文件或历史审稿报告尚未恢复，也不能把用户明确确认的“已审”误判成“未审”。

该确认**不得写入正式审核事件JSON**，不得虚构审核报告、逐章评分或AI味“通过”。源稿及报告未核实时，台账显示“已写（作者确认；文件待核）／已审（作者确认；报告待关联）”，有原正式终审登记则继续展示真实历史分数并注明当前版本待核。未收到作者明确确认时，仍严格使用文件和真实审核证据推断。新生成器必须读取此持久确认文件，不能在下一轮重新生成时清空作者确认。作者确认的是历史完成状态，不代表该卷后续任何新版稿件无需复审。

**2026-11-06已确认范围**：第一至四卷全部篇目四个阶段均已编写、均已审核；第五卷全部篇目四个阶段编写完成，其中卷纲、章纲已审核，简写、正文待审核。包括各卷独立插章，不对具体数值评分作任何补录。本规则不影响 `07-创作记忆/作者人工复核进度.md` 的只读保护。

## 标准操作

1. 完成阶段稿件/审核报告的实际落盘，按既有规范同步必要副本、质量登记及修订时间记录（此 Skill 不代替那些动作）。
2. 如本轮**确实完成了对指定成果物的审核且生成了正式报告**，先核对报告中已实际完成的“相邻上游一致性验收”及硬门禁结论，再运行下面命令录入本轮审核事件；对一卷全部章的审核，必须逐篇证据核实并分别登记。报告必须为仓库内已经存在的文件。
3. 执行生成命令刷新 MD + CSV；再次使用 `--check` 做一致性验证。输出总表章节数、已写、已审核、未审、需复审的统计，说明无法验证项；记录到本次交付。
4. 任何审核阶段被中断／工具无法写文件／只读授权覆盖整个仓库时，不虚报已更新；说明同步阻塞。GitHub 连接仅能改文本而无法在远端执行 Python 时，可以先写入真实、保守的记录并明确 **脚本检查尚未实际执行**，不要声称 PASS。**不创建PR，按仓库与作者指令直接改当前分支。**

```bash
# 从当前仓库真实文件重新生成所有20卷和每一篇有效章节的台账
python .agents/skills/novel-progress-ledger/scripts/update_progress_ledger.py --project-dir .

# 幂等检查（只读，发现台账落后则退出非零状态）
python .agents/skills/novel-progress-ledger/scripts/update_progress_ledger.py --project-dir . --check

# 例：第五卷第144章简写审核已经完成且报告已落盘，登记真实结论后刷新
python .agents/skills/novel-progress-ledger/scripts/update_progress_ledger.py --project-dir . --record-review --volume 5 --unit 第144章 --stage 简写 --result 通过 --score 87.0 --report '08-审稿/实际存在的简写审核报告.md'

# 例：第五卷卷纲审核
python .agents/skills/novel-progress-ledger/scripts/update_progress_ledger.py --project-dir . --record-review --volume 5 --stage 卷纲 --result 待复核 --report '08-审稿/实际存在的卷纲审核报告.md'
```

**注意**：示例评分87只是命令格式示范，不是任何实际章节的分数；不存在示例报告时命令必须失败。登记有时间戳、文件摘要、报告路径，不能把用户一句“给审核一下”直接登记为完成。已明确要求只读审核且禁止任何仓库写入时只报告，不落表。

## 同步责任

- `chinese-novelist/SKILL.md`：每次写作或审核闭环后，生成并校验台账；正文终审先按原协议更新官方终审注册表，然后再刷新进度表。
- `novel-setting-maintenance`：若安全修订影响卷纲、章纲或章节拆分，刷新台账；严禁因设定清理而改正文或简写。
- 项目 `AGENTS.md`：写作前可查台账定位下一步，写后校验；若台账与权威稿件冲突，先更新权威来源再生成，不能反过来用台账覆盖原稿。
