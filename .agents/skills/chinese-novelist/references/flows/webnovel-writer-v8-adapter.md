# Webnovel Writer v8 与《崖边戍卒》正文写作合并协议

来源：[lingfengQAQ/webnovel-writer v8](https://github.com/lingfengQAQ/webnovel-writer/tree/v8)，Scriptor 8.3.2；此处借鉴工作流并作独立适配，不复制其 GPL-3.0 源码，也不假定 DSH 工具已安装。

## 0. 职责与优先级

- 本仓 chinese-novelist 继续担任小说创作总控；webnovel-writer-bridge 负责从**作者已批准的简写**到候选正文、八维审读及修订的链路。
- 本书的世界观、角色主档、动态状态、时间线、伏笔、文风、书稿目录、审稿标准以 AGENTS.md 及 01—09 既有目录为唯一权威。webnovel-writer 的默认世界书、草稿目录、爽点密度和字数契约不覆盖这些事实。
- DSH Scriptor v8 的 novel_get_story_status / novel_delegate / novel_record_review_findings / novel_settle_chapter 等是**上游原生工作台的工具**。仅在真实安装了兼容 DSH 工作台、相关工具可调用、书仓目录映射经过核对且已经备份时运行。其他宿主（Codex/普通 Agent）使用本仓适配工作流，不能宣称运行过 DSH 原生服务或其原子沉淀。
- 不迁移成上游的第二套“真源区/定稿区”；本仓正式正文始终是 06-正文/ 下的 MD，06-正文-TXT/ 为只读生成副本。已经完成的章节绝不因合并而自动重写。

## 1. 起草门禁（先校准，后写正文）

1. 按 AGENTS.md 的六项 JIT 核验进度、分卷任务卡、最新正文、人物主档、时间轴和状态账本；发现已有正式正文时只允许作者明确授权的定向修改。
2. 执行现有“概要设定→约500字简写→逐章用户审核”，核对**该章**作者明确批准的依据。没有证据就止于简写，不能用上游默认自动流程跳过审核，也不能把上一章的通过延续到下一章。
3. 出场人物需要小传（多次出现、关键行动、插章有限视角主角、稳定匿名职能角色同等处理）；按初始所属阵营建档。战争/救援/撤民需核对真实人数、指挥权、装备能力、情报边界和后勤限制。
4. 将输入区别为：A 已确认事实、B 正文内角色证言或未核实线索、C 规划建议。只有 A 能约束事实，B 不允许冒充定论，C 不可直接写入账本。
5. 编号常规章沿用本书写作目标 4500—5000 中文汉字，遵守全局 4000—5000 字硬边界及实际检查器；**独立不编号插章不设上下限**，不得凑字、拆章或以字数打分。

## 2. 按 v8 组织十段自包含材料包

| 段 | 真源映射与核对重点 |
|---|---|
| 01 本章任务与确认细纲 | 05-写作计划/章节任务卡或插章任务卡、经作者批准的简写原文、起止状态 |
| 02 硬约束与禁区 | AGENTS.md、04-文风/禁用表达与常见问题.md、本章不可透露内容 |
| 03 当前事实与连续性 | 07-创作记忆/当前写作进度、人物实时状态、队伍编组状态 |
| 04 人物、关系、地点、组织与规则 | 02-人物/相关独立小传、人物关系与冲突、相关 01-世界观 专题 |
| 05 时间位置与信息边界 | 07-创作记忆/时间轴总账.json、事件时间线、章节时空和已知事实 |
| 06 伏笔与读者承诺 | 07-创作记忆/伏笔兑现记录、03-剧情/伏笔与秘密、本章应推进项 |
| 07 近期正文衔接 | 上一实写编号章节结尾、时间相邻插章、99-章节摘要 |
| 08 文风基准 | 04-文风/文风总规范、原创文风样例、已完成正文的本书语态 |
| 09 暂定与警告 | 未确认履历、情报、势力责任、未裁决的概要偏离和缺少证据 |
| 10 来源与版本 | 每个来源的相对路径、完整原文 SHA256、读取范围、缺失及审批证据 |

离线打包工具（只读取真源，写临时文件，不写正文）：

    python .agents/skills/chinese-novelist/scripts/make_webnovel_write_pack.py --project-dir . --chapter 39 --volume 第二卷 --source "02-人物/主角/陈渡.md"

插章用 --interlude-task 传入 05-写作计划/插章任务卡/ 中准确路径；--source 可重复追加本章实际人物小传及世界专题。材料包写入 .novel-work/，来源清单提供 SHA256 和缺项；**打包成功不代表简写已审核**。应人工核对批准记录与本章全部关键材料，不能只把文件路径发给隔离子 Agent。

## 3. v8 起草模式与草稿版本

- 每次只起草一章或一篇插章。真实可用时派单独 drafting 子 Agent，把完整十段材料和获批简写、禁区、自身语态、信息边界、作者排除项**内联**给它；它不读取主控私有上下文。宿主不能派子 Agent 时可由当前模型按本协议起草，明确记录“未创建独立子 Agent”，不伪造交接和回执。
- 正文围绕人物在当下的动机、行动、对方反应和后果展开。细节不能改变既定选择或新增神奇技能；不为追求钩子/反转强行插入转折。三方视角的选择必须有自身生存逻辑、信息盲区、行动和代价。
- 候选稿保留在 .novel-work/章节标识/稿1.md、稿2.md……；每次修改新建一版，保留父版和差异。只能选择**一份**当前待审稿，不能以最新文件名代替稿件选择。
- 草稿正文与候选事实分开；候选事实每条有“类别、主体、时点、正文证据、可信度”，含人物伤病/位置/装备/归属、伏笔埋设或兑现。角色猜测不写为事实，候选事实**不能直接回写权威账本**。
- 作者提供的原稿默认直接审读；未授权时不主动全文润色，更不能为了展示新版本强制重写作者文字。

## 4. v8 八维审读 + 本仓双重质量门禁

八维逐项输出原文证据、行号、P1/P2/P3、问题根因、最小修改方案和实际处置：
1. 章节结构；2. 人物与关系；3. 情节与因果；4. 信息披露；
5. 线索与伏笔；6. 节奏与张力；7. 读者承诺；8. 文风与表达。

**八维是增量审读，而不是取代既有七维评分/八项质检**。继续使用 08-审稿/章节审稿与质检标准.md 和现有 scan_chapter.py、scan_ai_tone.py、verify_chapter_consistency.py 等检查器。G1—G4 四关及 ai-style-red-team-reviewer 独立反方审稿**始终是必经关卡**；反方必须专查同构动作、装备反复、无意义救援复述、副词形容词密度、声口雷同、场景无边际增量，且必须提供反证。缺少真实子 Agent 能力时标注降级，不能虚报已派生。统计词频是问题线索，不代表 AI 写作概率；同一问题不能双重扣分。

所有审稿发现项绑定当前稿件版本及参与核对的真源哈希；正文、获批细纲或关键材料改变后旧 PASS 自动失效，按影响范围复检。P1/P2 未处理、四关 BLOCKED、时间轴/人设硬伤或需要建档的角色无档时，禁止进入交付阶段。

### 改稿前的逐项净收益评估（不可略过）

执行 `references/guides/change-benefit-gate.md`：对于八维审读、G1—G4、独立反方及一致性报告中的**每一项候选修改**，先记录原文功能、证据与问题、预期改善、对人物/节奏/伏笔/信息披露/跨章连续性的潜在损害，对照原文和最小替代方案。**只有净收益明确为正（好处 > 坏处）才允许改稿**；收益相当、弊大于利或无法举证则保留/待核。P0/P1 或硬性门禁不能以不改假装 PASS，改法不合格应寻找更小替代，否则维持 BLOCKED 并交作者裁决。每条有唯一改动 ID，按独立可回滚单元执行；改后复审实际收益与新伤害，不值则回滚。将执行、保留、待决、回滚四类汇总进审稿报告。

## 5. 分项修订、候选事实沉淀与交付

- 根据证据分类：“只改正文 / 涉及世界观或大纲权威修改 / 作者保留 / 无法确定”。属于上游事实变动时先报告并取得批准；不能靠润色删除已确认的因果。
- 改稿执行者按“发现项编号→原文位置→修改位置→是否改变事实”逐条说明，优先局部修订；有实际变化才新增版本。改后重跑相关八维、G1—G4、独立反方及动态状态检查。连续三轮仍未收敛则报告瓶颈交作者决策，不能擅自放行。
- 审稿通过后由人/Agent对每条候选事实复核“谁、何时、发生了什么、哪段正文支持”，确认后才回写 07-创作记忆/ 和人物小传，记录生效章节。未证实传言/未批准未来计划永远不能写成已发生事实。
- 将被选定且通过本仓审稿的**纯正文**落至既有 06-正文/<卷>/第NNN章.md 或已有插章文件名；上游稿件 frontmatter、候选事实和审稿元信息绝不混入小说正文。
- 运行 export_reading_txt.py 按单章刷新 TXT 和分卷合订本，最后用 --all --check 检查同步；权威 MD 改动后需重新同步。完成报告写明草稿/正式稿、审批证据、材料哈希、八维发现项、原四关和反方执行状态、账本变更及未解决阻断。
- 原生 Scriptor 的定稿裁决与 retcon 工具只有在真正具备工具和作者裁决时使用；不能手写伪造的原生审核 JSON、原生提交状态或自动创建第二套世界书。项目直接 Git 提交遵守仓库既定权限与用户授权。

## 6. 对接和升级

以 v8 正式版为流程来源，**不把 master(v6) 的 Claude Code 插件当 v8 调用**。v8 依赖 DSH，未验证存在旧书仓直接迁移能力，不得自动迁移和覆盖第一卷插章及已完成第001—039章。升级 v8 需先检查 release、工具契约、GPL-3.0 依赖与备份，再调整本适配层。

**示例说明**：上述第039章命令只用于核验已有任务卡的只读备料，不是重写第039章的许可；后续新章必须先存在任务卡并完成简写审批。脚本输出的 author_approval_verified 永远为 false，必须由主控另行核对实际作者批准记录。
