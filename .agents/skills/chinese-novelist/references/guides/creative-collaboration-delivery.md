# 创作讨论与结果交付（通用协作方法）

> 最后修订时间：2026-11-11 22:09:18 +08:00
>
> 用途：明确“构思讨论”和“执行既定写作／审核”的不同模式，减少无效追问、未经确认的脑补，以及无法执行的空泛审稿建议。借鉴 [zephyr-skills](https://github.com/zephyrw/zephyr-skills) 中构思交互、易读计划与简练完整表达的思路，针对已有四阶段创作、台账和正式审核流程独立改写。**本文件只优化协作及说明方式，不覆盖主 Skill 的写作顺序、作者权限、实际工具与审核协议。**

## 一、先辨认任务模式，不给作者重复布置作业

| 用户现在要做什么 | 正确响应 |
| --- | --- |
| 零起点讨论创意、寻找卷级看点 | 先确定具体事件，再用可比较的方案发散；必要时一次只问一个会改变方向的关键问题 |
| 只有一张画面或一个奇物设定 | 说明这是局部素材，给出可能发展成完整事件的不同机制，不自动认定故事已定 |
| 已提供总纲／章纲、要求直接生成成果物 | 读取有效项目资料并执行对应阶段及写作准入；不强迫作者重新选题、不照搬“只做大纲”的外部 Skill 限制 |
| 用户要求先看一份试纲／方案 | 根据当前材料交付可读的临时版本，注明假设和候选；若要正式写入权威文件，仍须核对阶段权限和版本门禁 |
| 用户指定章节要求审核或修订 | 直接按现有审核入口读取目标全篇、权威事实及必要邻章，出有证据的结论；不连续追问已知信息 |
| 作者说“这段不好看／太套路” | 尽量先指出问题在事件机制、人物动机、信息投放还是句子表达，不用一律“加反派／加事故／加反转”处理 |

只有答案会改变**核心事件、关键人物决定、事实一致性或作者授权边界**，且当前资料无法核实时，才值得向作者追问；普通写作细节在不编造设定的前提下直接处理。构思对话每轮最多询问一个关键决策问题；如果已能按要求产出，不因想凑互动轮数而停工。

## 二、将候选、设定和已发生事实分层

讨论时可在内部维护简短状态：作者已明确确认的意图及禁区；当前核心事件；未确认的候选；尚存的关键缺口；下一步最有价值的决定。只有需要帮助作者决策时才展示相关部分，**不将内部清单变成每回合的问卷**。

应区分：
- **已发生事实**：已经写入并确认的正文结果，按主 Skill 与项目权威资料保护。
- **已确认约束**：作者明确敲定且有效的设定、主线、规划及锁定伏笔。
- **待定候选**：讨论中提出、作者未选择的想法，不得无标记进入章纲、简写、正文、设定库或审核事实依据。
- **未经核实的判断**：来自推测、工具提示或缺失材料，必须明确“待核实”，不得包装成客观证据。

作者否定一条候选时，撤回由它推演的未定支线；作者只修改其中一处时，追踪相关因果和知情链，**仅影响所需范围**，遵守项目的修订时间记录与下游影响清单规则。

## 三、按使用者阅读顺序交付

**构思方案或卷纲说明**：先让读者明白当前事件和核心看点，再说明目前困境、人物目标、为什么选择这个机制、主要阶段走向与代价，最后列确有必要的设定依据、待确认差异及阶段交接。不把文件路径、人物卡字段和几百条待办贴在第一屏，让别人自己拼主线。

**正式审核报告**：先给范围与结论，紧接真实版本／可读材料及阻塞，再给可定位的问题、正文或章纲证据、影响、最小修改方向及复验结果；完整的七维／16维原量表、AI味37项、台账与同步状态必须按现行协议保留，**不能为了简洁省略强制结果**。每条重要建议应写清“要解决什么问题、怎样改、怎样验证”，而不只写“增强张力”“优化人设”。

**简短任务答复**：先说明已完成的改动与文件、无法完成的部分、当前验证状态，再补充最必要的后续动作。过程流水账不代替结果；不要声称没有真实执行的审核、同步、提交或验证已完成。

## 四、交付前四步核对（不新增评分）

1. **完整**：实际要求、项目强制字段与仍待处理的限制是否都交代了？
2. **可辨**：作者决定、既成事实、临时方案、推断与未知是否被明确区分？
3. **有用**：每项修订或任务是否有清楚的作用、对应证据、实施动作与验收方式？
4. **好读**：用户能否只看开头和重要结论就掌握事情，技术细节及核验清单能否放在其后，且没有删掉必要条件？

这些是对外说明与协作检查，**不用于压缩小说正文、削减人物互动、替换场景叙述或缩短作者要求的篇幅**。小说的节奏、留白、生活质地及对白由正文创作规则与真实阅读体验决定。
